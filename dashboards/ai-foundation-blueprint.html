一、定位与设计原则

AI Foundation 是什么（本讨论稿的定义）：企业自建的、支撑所有业务 AI 应用的公共底座——让每个业务团队做 AI 应用时不必重复造轮子，同时让安全、合规、成本在底座层统一管控。

Workshop 阶段的四条设计原则（决定所有后续选型）：
① 供应商中立——底座不绑死任何一家模型厂商（OpenAI/Anthropic/国产），今天的热门模型 18 个月后可能被替换，接口层必须可插拔；
② 能力分层——底座只提供"每个应用都需要"的能力（模型接入/知识/工具/审计），业务特性留给应用层；
③ 安全左移——13 份权威报告的交叉共识：Agent 时代最大的风险（提示注入/过度授权/凭证泄露）只能靠架构层缓解，无法事后修补（ OWASP Agentic T6：数据与指令不可分是架构级问题）；
④ 小步快跑——底座按能力分阶段交付，每阶段都有可用产出，不做"建成再用"的大瀑布。

二、六层参考架构（High Level）

每层只回答"这一层放什么、为什么必须有"。产品选型在 workshop 后做。

L1 · 模型接入层 MODEL GATEWAY

放什么：统一的 LLM 调用网关——所有应用通过它访问任何模型（商用 API / 开源自部署 / 本地小模型），统一鉴权、限流、计费、failover。

为什么第一层是这个：供应商中立的物理保证。今天用 GPT 明天换国产，应用代码零改动。这是兼容性最强的一层，也是成本可视化的前提。

参考形态：OpenAI 兼容协议已成为事实标准（包括国产模型基本都兼容）；开源网关（LiteLLM 类）或云厂商网关皆可。

L2 · 知识与数据层 RAG & DATA

放什么：企业知识的统一入口——文档向量化、检索增强（RAG）管道、数据脱敏/分级。业务应用"提问"，这层负责"给对的知识"。

为什么：杜绝每个应用各建一套知识库（重复建设+权限口径不一致）。数据分级在这里统一执行：什么数据可以进 prompt，什么必须脱敏。

关键约束：权限模型必须与现有身份体系对齐——用户能检索到的内容 ≤ 其原有权限（防止 RAG 成为越权读取的后门）。

L3 · 工具与代理层 AGENT & TOOLING

放什么：AI 调用企业系统的"手"——工具注册中心（MCP/Function Call 统一管理）、Agent 运行时、沙箱执行环境。

为什么：这是权威报告警告最多的层。OWASP Agentic Top10 的核心结论：过度授权（Excessive Agency）是唯一能在设计阶段完全消除的风险，但现实中普遍违反（"先跑起来再说"文化）。工具中心化注册 = 每个工具的权限/审计/版本有统一台账。

关键约束：第三方 MCP/工具必须经安全评审后入库（供应链风险：mcp.so 已收录 1.6 万+公开服务器，正复刻 npm 蛮荒期——JFrog 已发现波及全生态的组件漏洞 CVE-2025-6514）。

L4 · 身份与权限层 IDENTITY

放什么：人和 Agent 的统一身份体系——Agent 的服务身份、凭证保管（Vault）、最小权限、人类审批关卡（human-in-the-loop）。

为什么：三份独立报告同指一个事实：现有身份体系为"人操作电脑"设计，Agent 是"软件操作软件"（机器身份:人类身份已达 109:1——CyberArk 数据）。凭证泄露是 ADR 生产数据中最先爆发的风险（10 个月 26 类高危凭证外泄，且大多非恶意——员工顺手把密钥贴进 prompt）。

关键约束：高危操作（付款/删除/外发）默认人类确认；Agent 凭证永不落盘、自动轮转。

L5 · 可观测与审计层 OBSERVABILITY & AUDIT

放什么：全量行为日志（prompt/工具调用/数据访问/决策链）、审计检索、合规报告、异常检测。

为什么：传统 SOC 看得见"动作"看不见"意图"（EDR 能看到文件写入，看不到 Agent 为什么写——Uber ADR 原文）。OWASP Agentic T8 将"不可追溯"单列为 Top 风险。OpenAI×HF 事件（2026-07）实证：700 个 Agent 的异常行为淹没在海量日志里一周无人发现——日志必须配 AI 规模的分析能力，这层与 SOC 的 LLM 研判方向天然融合。

关键约束：日志记录"因果链"（prompt→推理→工具→结果），不只是 API 调用记录——否则事后无法取证。

L6 · 治理与策略层 GOVERNANCE

放什么：AI 使用政策（能做什么/不能做什么）、模型准入标准（安全评估）、数据分类策略、红队测试机制、事件响应流程。

为什么：NIST AI RMF 的四函数（治理/映射/测量/管理）中，治理排第一。IBM 2026 报告新增"影子 AI"为泄露主因——没有官方供给，员工就会用私人 AI 处理公司数据；治理不是限制使用，而是把需求导入受控通道。

关键约束：政策要"可执行"（技术上能拦截），不是 PDF 文件。

六层的兼容性设计：L1 保证模型可换、L2/L3 保证知识库和工具不绑应用、L4/L5 对接现有 IAM 和日志体系（不推倒重来）、L6 是制度层零技术依赖。任何一层都可以先独立起步，后拼成整体。

三、分阶段路线（供讨论）

阶段交付解决什么痛点依赖
Phase 1（0-3月）
受控试点		L1 网关（2-3 个模型接入）+ L6 最小政策（使用规范/数据分级）影子 AI——给员工官方通道，用量和成本立即可见几乎无依赖，最快见效
Phase 2（3-6月）
知识与工具		L2 RAG 管道（1-2 个高价值知识域）+ L3 工具注册中心（首批内部 API）应用重复建设；RAG 权限统一L1（流量统一走网关）
Phase 3（6-12月）
代理规模化		L4 身份层（Agent 服务身份+Vault）+ L5 审计（接入 Splunk/SOC）Agent 上生产前的安全门槛L3（有工具才谈权限）；对接现有 IAM
Phase 4（持续）
运营化		红队常态演练 / 模型评估流水线 / 度量看板持续合规与风险跟踪前三阶段全部就位

阶段划分的逻辑：先"给通道"（堵不如疏），再"给能力"（知识/工具），最后"给护栏"（身份/审计）——每阶段独立有价值，workshop 上可以按公司实际痛点重排优先级。

四、治理与度量（Workshop 必谈）

维度建议度量依据
采用度官方通道 vs 影子 AI 的流量比；活跃应用数IBM：影子 AI 是新泄露面——度量它才能治理它
成本每应用/每部门的 token 成本与 ROIL1 网关天然产出此数据
风险高危工具调用拦截数；凭证异常使用告警数；红队发现数OWASP Agentic T8（可追溯）；ADR（凭证最先爆）
质量模型评估基准分；幻觉率抽检；用户满意度NIST AI RMF "测量"函数
与现有体系的融合点（不另起炉灶）：身份 → 现有 IAM/AD；审计 → 现有 Splunk/SOC（LLM 研判方向已在规划）；数据分级 → 现有数据安全制度；事件响应 → 现有应急流程加"AI 事件"分支。Foundation 是放大器，不是替代品。

五、留给 Workshop 的五个讨论题

  • ① 首个场景选什么？（客服/研发/知识问答/数据分析——建议选"数据不出公司+容错高"的场景打样）
  • ② 模型策略：纯国产 API / 混合（内部数据走国产+外部任务走国际）/ 自部署开源？——数据分级决定模型准入
  • ③ 自建 vs 采购：六层里哪几层必须自持（建议 L1/L4/L5 自持——它们是控制点），哪几层可采购（L2/L3 有成熟产品）
  • ④ 组织归属：Foundation 放数字化部门还是 IT 基础架构团队？安全团队在其中的角色（共建 L4/L5）
  • ⑤ 投入产出怎么向管理层呈现：建议用"影子 AI 治理 + 成本可视 + 安全合规"三重叙事（均有权威报告数据背书）
